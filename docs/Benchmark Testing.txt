
NOTE: THIS BENCHMARK SYSTEM WAS MADE *BEFORE* VIRTUES WERE ADDED TO LGO!

How many items can optimizer handle in the pool before it becomes unbearably slow? The built-in benchmark test is a benchmark harness that measures exact-search cost as candidate pools grow under the current hand-pool semantics, without changing any production search path.

Benchmark testing has produced the following answers to that question and others:

  Recommendations:
    . If your optimization runs are far too slow, try reducing the number of goals you are trying to meet simultaneously. This will have a much larger effect than removing items from your pool.

    . No reasonable number of items has produced significant performance degradation in benchmarking. For a player to have, for example, 10 items for every slot, they would need to use all or nearly all of their shared storage space, and with four stated goals, the intense slow-down only occurs when there are more than 20 items for every slot. It is expected that no reasonable use of the optimizer will ever average more than 6 or 8 items per slot at most.
  
    . The number of goals is far more of a constraint. At 9 goals, even 8 items per slot *can be* unmanageably slow.
  
    . But by far the biggest effects on performance are the goal values. The optimizer's run time depends mostly on how ambitious your stat goals are. Specifically, the closer your stat-goal values are to what is maximally achievable, without going *way* over it, the more computationally intensive will be the optimizer's run. Goals that are easy for your gear, or far beyond it, resolve quickly. Goals near the edge of what your gear can jointly achieve — where the optimizer must weigh real trade-offs between them — are what take time, and each additional borderline goal multiplies the effort. If a run is too slow, the fastest fix is to relax or remove the minima you care least about, not to reduce your item pool.
      . Hard: 
        . Stat goals near the limit of what is achievable with your gear.
        . All slots have the same or nearly the same numbers of candidate items.
      . Easy:
        . All stat goals at or near the same values.
        . Slots have widely differing numbers of candidate items. (Having 2 candidate items for one slot and 8 for a second slot is much faster than having 5 for each)
        
    . If what you want is maximize as single stat, set exactly one goal. Additional goals with very low minima barely influence the result (they only break exact ties) but can slow the optimizer enormously.

The test code resides in `src/optimizer` at the top of the TESTS section, around line 850 or so (at the time of this writing). 

Editable parameters:
  . const TIME_LIMIT_SECS: u64 = 100; — the knob: per-run cutoff, with a comment marking it as the thing to edit.
  . const BENCHMARK_GOALS: [(Stat, i64); 4] — the fixed 4-goal set. Editable, but changing it invalidates comparability with prior runs, so leave it unless you have a reason.
  . BENCHMARK_BASELINE_SLOT_CANDIDATES: This sets the baseline item count for slots/families that are not varied by the selected profile.
  . BENCHMARK_BASELINE_HAND_CANDIDATES: This sets the baseline item count for the combined hand pool when it is not varied by the selected profile.
  . MAX_N: The value of 'N' past which the tests will stop. (In case the tests are still not exceeding 'TIME_LIMIT_SECS'.)

(Do not edit BENCHMARK_SINGLETON_SLOTS / BENCHMARK_PAIRED_FAMILIES. These are structural constants)

Virtues: every run also appends the real Virtue family (all 21 Virtues from `data/lgo_virtues.json`, derived for a Lore-master with the committed `data/base_stat_derivations.json`) as the last search pool, exactly as production does. The `virtue supers` column reports the size of that pool after the >=5-dominators pre-filter, the 5-combination enumeration and the combo dominance filter. It does not depend on N or the profile; under the fixed BENCHMARK_GOALS it is measured at 74 (21 Virtues -> 12 pre-filter survivors -> C(12,5) = 792 combinations -> 74 super-candidates).

  How the last pool is bounded (Bug 16 in `docs/BUG_HISTORY.md`): the branch-and-bound sums each remaining pool's per-goal maxima, EXCEPT for the last pool, which is bounded by iterating its real candidates (prune only if every one of them loses to the best so far). A per-goal-max over 74 five-sets is a fantasy set (max CR from one set, max TT from another) far better than any real set; with that bound the Uniform profile did not complete at N = 8 at all. With the per-candidate bound the Virtue pool costs essentially nothing, which is why the pool goes last.

  Note on comparability: adding the Virtue pool changed the REGIME the benchmark runs in, even though BENCHMARK_GOALS are unchanged. Without Virtues the synthetic gear could never reach TacticalMitigation 11,000 (TT per item is 0..4 until the first TT-primary item at index 12), so N <= 12 ran in Stage 2 (maximise the unmet TT) and cost 85k..8.8M nodes. With Virtues, TT and PhysicalMastery are met by the Virtue set alone, so N <= 12 runs in Stage 3 (raw lexicographic polish) where the synthetic CR frontier collapses to a few hundred nodes. N = 13 breaches on both: that is where the index-12 item (TT 8,002 at -2,400 CR) appears and the component-wise GEAR bound starts crediting its TT alongside index 0's CR in the same slot. Node counts before and after PR #92 are therefore not comparable for N <= 12; the breach point is.

The test can run any of four separate 'Profiles', named in enum 'BenchmarkProfile' :
  . Uniform
  . SinglesAtN
  . PairsAtN
  . HandsAtN

Profile         What grows with N              What it answers
-------         -----------------              ---------------
Uniform	        Everything at once             Worst case: if every pool has N items, what's affordable?

Singles-at-N    Only the 11 singleton slots    How costly is growth in singleton slots?

Pairs-at-N	    Only Wrist/Finger/Ear          How fast does the quadratic pair expansion hurt?

Hands-at-N      Only the combined hand pool    How costly is growth in the hand pool?


# To run all four profiles in one go (fine if nothing times out):
LGO_RUN_BENCH=1 cargo test --release benchmark_candidate_scaling -- --ignored --nocapture | tee bench_all.txt

# Per-profile isolation (after any timeout, or for clean measurements):
LGO_RUN_BENCH=1 LGO_BENCH_PROFILE=Uniform cargo test --release benchmark_candidate_scaling -- --ignored --nocapture | tee bench_uniform.txt
LGO_RUN_BENCH=1 LGO_BENCH_PROFILE=Singles cargo test --release benchmark_candidate_scaling -- --ignored --nocapture | tee bench_singles.txt
LGO_RUN_BENCH=1 LGO_BENCH_PROFILE=Pairs   cargo test --release benchmark_candidate_scaling -- --ignored --nocapture | tee bench_pairs.txt
LGO_RUN_BENCH=1 LGO_BENCH_PROFILE=Hands   cargo test --release benchmark_candidate_scaling -- --ignored --nocapture | tee bench_hands.txt
