## Why this PR exists
The current optimizer reasons from **independent per-slot/per-stat maxima**,
which do not compose into feasible complete builds (see the audit chain in
`docs/Optimizer_Overhaul/01`–`06`). It also implements the WRONG objective: it
maximizes raw stat 1, then raw stat 2, etc. The correct objective (below) is a
**clamped-satisfaction** model. Both the search core and the objective are being
replaced. This is a rewrite, not a bug fix — be liberal in deleting the old
search code and the tests that encode the old semantics.

## The objective function (authoritative — implement EXACTLY)
Only **goal stats** participate in the search or the objective. Non-goal stats
are summed/stored on chosen items for display but never influence the search.

For each goal with minimum `M` and achieved total `v`, define a **clamped
score**: if `M > 0`, `score = min(v / M, 1.0)`; if `M == 0`, the goal has no
floor — treat it as always "met" for satisfaction, and use its raw value only in
Stage 3.

Compare two complete builds X and Y by these stages, in order; the first stage
that distinguishes them decides:

1. **Met-vector, lexicographic in priority order.** Each goal contributes `1` if
   its minimum is met (`M == 0` counts as met), else `0`. Compare the met-vectors
   as tuples in priority order; greater wins. (This single rule yields the
   "ratchet": crossing a higher-priority goal into *met* justifies dropping a
   lower goal, but merely raising an unmet-and-still-unmet higher goal does not.)
2. **Clamped-score vector, lexicographic in priority order.** Among builds tied
   on the met-vector, compare clamped scores in priority order; greater wins.
   (Because met goals clamp to 1.0, this only differentiates goals that are
   unmet in both builds, getting the higher-priority unmet goal closest to 100%.)
3. **Raw-value min-max polish, lexicographic in priority order.** Among builds
   tied on the entire clamped-score vector, prefer higher RAW goal totals in
   priority order. (Never sacrifices satisfaction — Stages 1–2 already settled
   that — only picks the biggest headline numbers among equivalent builds.)
4. **Deterministic final tiebreak.** Exact ties above are astronomically rare;
   break them by a stable arbitrary key (e.g. sorted chosen-candidate instance
   keys) so output is reproducible. No product meaning.

**Feasibility flag:** feasible iff every goal with `M > 0` is met (met-vector all
1s on floored goals). Reported separately; the optimizer always returns its best
build under the comparator, feasible or not. There is NO separate "infeasible
fallback" path — the comparator handles feasible and infeasible uniformly.

### 2. `src/optimizer.rs` — the comparator
Implement the Stage 1–4 comparator above as a single total ordering over a
build's goal-stat totals, e.g. a function
`fn compare_builds(x_totals: &[i64], y_totals: &[i64], goals: &[StatGoal]) -> Ordering`
(operate on goal totals in goal order). Unit-test it directly with the worked-
examples table BEFORE wiring it into search, so the objective is verified in
isolation. Use integer/rational math (avoid float equality pitfalls): compare
`v/M` clamped without floating point where practical — e.g. compare `min(v,M) * M'`
cross-multiplied, or compare the pair `(min(v,M), M)` as an exact rational. Met
= `v >= M`. Guard `M == 0` (no division).

### 3. `src/optimizer.rs` — the production search (exact)
Replace the old search with an **exact** search that returns the comparator-
maximal complete build. Two required components:

**(a) Per-slot dominance pre-filter.** Within each slot pool (single slots AND
paired-family pools, operating on the pair super-candidates), discard any
candidate that is `<=` another candidate in the SAME pool on EVERY goal stat.
Keep exactly one survivor among exact ties (equal on all goal stats). Rationale:
stats are additive and the objective is monotonic non-decreasing in each goal
total up to its clamp, so a dominated candidate can never be uniquely required.
Only goal stats matter for dominance (non-goal stats are irrelevant to the
objective, per spec). This must be proven safe by the fuzzer (below).

**(b) Branch-and-bound over slots.** DFS one slot at a time over the (dominance-
filtered) pools, tracking running goal totals. Maintain the best complete build
found so far under the comparator. Prune a partial build when its **optimistic
completion** — running totals plus, for each remaining slot, that slot's per-goal
maximum — cannot beat the best-so-far under the comparator. The bound must be
**admissible** (never underestimate achievable goal totals), which keeps the
search exact. If pruning ever changes the RESULT vs. the oracle, that is a bug
(the fuzzer will catch it).

**Determinism:** iterate slots in `Slot::ALL` order and candidates in a stable
sorted order so results are reproducible.

**Empty/placeholder slots and singleton paired families:** preserve current
behavior (zero placeholders for missing slots; a singleton paired item pairs
with an empty placeholder, never itself — `build_pairs` already does this).

### 4. `src/optimizer.rs` — assembly & result
Assemble the winning build into a `GearSet` exactly as today (one item per slot;
for paired families, place the two constituent items into slot1/slot2). Recompute
`feasible` and `failed_minima` from the assembled totals (keep this honest final
check). `OptimizeResult` shape is unchanged unless a field is genuinely needed.

## Differential fuzzer
Add a deterministic (seeded RNG) differential test comparing production
`optimize` vs. the oracle:
- **Input contract:** stay within supported bounds — 2–4 slot families total
  (include a paired family sometimes), 1–4 candidates per slot/family (? cap),
  1–3 goals, small stat ranges (e.g. 0..=15, include some zeros and occasional
  negatives), minima in a small range (include some `:0`).
- **Compare:** feasibility flag AND the clamped-score vector (equivalently: the
  comparator judges them equal). Do NOT require identical item identity — ties
  may pick different but equivalent builds.
- **On mismatch:** print goals, all slot pools + candidates, both results, and a
  copy-pasteable fixture; fail. Any discovered mismatch should be promoted to a
  permanent deterministic regression test.
- **Volume:** ~250 cases in a normal `#[test]`; a deeper run (5,000+) behind
  `#[ignore]` (documented in `docs/Command Line Reference.txt` §4 as
  `cargo test -- --ignored`).

- `cargo build`, `cargo test`, `cargo clippy`, `cargo fmt --check` all clean.
- The comparator matches all five worked examples.
- Production `optimize` matches the oracle on the fuzzer (250-case normal run and
  the deep `#[ignore]` run).
- The five real observed cases from `docs/Optimizer_Overhaul/01` (e.g.
  `cr:100000 tm:70000`) behave per the new objective: a lower-priority goal is
  NOT missed while a higher-priority goal sits far above its met threshold, when

  description; they are expected to differ from the old ones.)
- No candidate is ever silently dropped (overflow refuses via PR-1 guard;
  dominance only drops provably-dominated items).
